## What keeps the splash up

The splash is hidden in one place, `app/_layout.tsx:307-316`:

```ts
const ready =
  (fontsLoaded || !!fontError) &&
  themeReady &&
  isAuthed !== null &&
  i18nReady &&
  !(isAuthed === true && onboardingCompleted === null)

useEffect(() => { if (ready) SplashScreen.hideAsync().catch(() => {}) }, [ready])
```

Until `ready` is true, `RootLayout` renders only a blank `View`. None of the app tree mounts, so `UpdateRequiredGate`, the API config and the minimum-version check can't be holding the splash. They only mount after it hides.

Here is each gate and whether it can hang:

| Gate | Source | Can it stay stuck? |
|---|---|---|
| `fontsLoaded \|\| fontError` | `useFonts(presetFonts)` | Unlikely. A failed font sets `fontError`, which counts as done. |
| `themeReady` | `loadThemePref()` + `loadHapticsPref()` with `.finally` | No. Both catch their own errors, and `.finally` always runs. |
| `i18nReady` | `initI18n().then(() => setI18nReady(true))`, line 212 | **Yes, silently.** There's no `.catch`. If `AsyncStorage.getItem('app_language')` or `i18next.init` rejects, `i18nReady` never becomes true. |
| `isAuthed !== null` | `supabase.auth.getSession()`, line 237 | **Yes, while the promise is pending.** The `.catch` handles a rejection but not a hang (see below). |
| `onboardingCompleted` when authed | set in the same `.then` as `isAuthed` | No. Every path that sets `isAuthed = true` also sets it. |
| `hideAsync()` itself | line 315 | **Possible.** Errors are swallowed by `.catch(() => {})`, so if the native call fails, `ready` is true but the splash stays up. |

**The two likely causes:**

1. **`getSession()` hasn't settled.** If a session from an earlier run is stored in the Simulator and its access token has expired, `getSession()` waits for a refresh. That refresh (`@supabase/auth-js` 2.108.2, `_refreshAccessToken`) is a `fetch` with no timeout, retried with backoff for up to about 30s. If the Supabase host doesn't answer (a LAN IP that changed, a local stack that isn't running, a dead tunnel), each attempt waits for iOS's roughly 60s network timeout. Nothing throws, so nothing is logged. It looks like "forever", but it should eventually clear or fail.
2. **`initI18n()` rejected.** This is the only gate with no failure path, and it's the only one that would truly hang forever. The resulting "Possible unhandled promise rejection" warning is easy to miss.

If Supabase were unconfigured, you'd see `Supabase is not configured…` in Metro and auth would resolve immediately. Seeing no such line suggests it is configured, which makes cause 1 plausible.

## How to find the stuck gate (no code changes)

1. **Inspect `RootLayout`'s state in React DevTools.** Press `j` in the Metro terminal to open React Native DevTools, then go to the **Components** tab and select `RootLayout` (inside Sentry's wrapper). The hooks appear in source order:
   - `Fonts` → `[loaded, error]`
   - `State` (1st) → `themeReady`
   - `State` (2nd) → `isAuthed` (`null` means `getSession` is still pending)
   - `State` (3rd) → `onboardingCompleted`
   - `State` (4th) → `i18nReady`

   Whichever value is still `false` or `null` is the stuck gate. If all are satisfied and `AppTree` is mounted under it, the problem is `hideAsync()` (step 4).
2. **Test the Supabase theory.** In DevTools, open the **Network** panel and relaunch. A pending `POST …/auth/v1/token?grant_type=refresh_token` confirms it. As a cross-check, wait about 2 minutes: if the splash eventually clears, it's the refresh. Or erase the stored session (Simulator → Device → Erase All Content and Settings, or uninstall the app) and relaunch. If the splash hides right away on the welcome screen, a stored session plus an unreachable Supabase host was the cause.
3. **Check i18n.** In the DevTools **Console**, filter for `unhandled`. A "Possible unhandled promise rejection" that mentions AsyncStorage or i18next means `i18nReady` is the gate.
4. **If every gate is satisfied**, suspect the native build. It may be stale relative to the JS, since the fingerprint runtime changes whenever native config does. Run `npx expo run:ios` from `apps/mobile` (not the repo root) to rebuild the dev client.

   There's a related clue at the repo root: a stray untracked `app.json` with `"bundleIdentifier": "com.anonymous.app-template"`. That's what Expo writes when it's run from the root, so a build may have been generated from the wrong directory at some point. It's worth deleting once you've confirmed nothing uses it.

Once you know which gate it is, the fix is small. For i18n, add a `.catch` that still sets `i18nReady`. For Supabase, put a timeout on the startup `getSession` so the app falls through to signed-out or offline. For `hideAsync`, log instead of swallowing the error.
