Yes, it has to be capped, and the cap should be decided now. Here's how I'd design it.

## Where it lives: in the database, on the server

A new `pet_memories` table, next to `pets` and `pet_needs`. Not on the phone, because:
- **Reinstalling or switching phones** would wipe a memory kept on the phone. A pet that forgets you is the opposite of the product.
- **The server builds the prompt.** If the phone sent its memories, the server would be trusting whatever the phone says.
- **Deleting it is simple.** Seeing and deleting what the pet remembers goes through one route. Deleting the pet or the account deletes its memories too.

The short-term memory stays as it is now: the last 3 exchanges, kept on the phone.

## What gets stored: short facts, never the conversation

We never store what was said. After each reply, the model can return **at most one** short fact (max ~80 characters), in the same call, as one more field:

```
"Has an exam on Friday"
"Has a sister called Ece"
"Loves football, supports Galatasaray"
```

Each fact is about 15 tokens. Sensitive topics are never kept: health, religion, politics, sexuality, money. The prompt says so, and the server filters on top of that.

## How big: a fixed cap

| | Proposal |
|---|---|
| Facts stored per pet | **30** (Plus: 100, see question 2 below) |
| Facts sent with each message | **up to 6** (~100 tokens) |
| Database size | 30 rows × ~100 bytes. Nothing. |
| Extra cost per message | ~+10–15% input tokens, a fraction of a cent a month |

**We never send all of them.** The model sees: personality, needs, **up to 6 chosen facts**, the last 3 exchanges, and your message. The prompt stays the same size whether you've used the app for a week or a year.

## Which 6 get chosen

The server scores each fact, with no embeddings or vector search for v2:
- **It matches what you just said.** You mention "exam", so the exam fact gets picked.
- **It has a follow-up due.** "Exam on Friday" is due on Saturday, so the pet asks how it went.
- **It's important.** People, pets and big things in your life score above "likes pizza".
- **It hasn't come up recently.** So the pet doesn't repeat the same fact every message.

## Does it remember something from 3–4 months ago?

**It depends on the kind of fact**, and the model labels each fact with its kind:

| Kind | Example | How long it lasts |
|---|---|---|
| **Lasting** | "Sister called Ece", "has a dog named Kara" | **Months**, until it's corrected or pushed out by the cap |
| **Event** | "Exam on Friday", "job interview tomorrow" | **About 2 weeks**: asked about once after the date, then deleted |

So after 4 months it still knows your sister's name, but not that you had a cold in July. That's how a friend remembers too.

**When the 30 slots are full**, the lowest-scored fact is dropped: old, never brought up again, not important.

**When a fact changes** ("I moved to Berlin"), the model can say "replace fact #12" instead of adding a new one. It sees the list of current facts, so it can catch the duplicate.

## Privacy, which store review requires

- You can see and delete what the pet remembers, on the pet's page: "Mochi remembers…" with a delete on each fact.
- One sentence in the privacy text.

## Two decisions for you

1. **Do the numbers work?** 30 facts stored, 6 sent per message, events forgotten after about 2 weeks.
2. **Is memory part of Plus?** My suggestion: everyone gets memory (it's the core feeling, so don't paywall it), but **Plus remembers more** (100 facts instead of 30). That gives the paywall a line that fits the product: "Mochi remembers more about you."

For the reviewer message, one clause covers this: *"short facts, capped at 30 per pet; only the 6 most relevant go into each message, so cost doesn't grow with time."* Want me to add it to the draft?

## How the 6 are picked

The server already has your message as text before it calls the model (speech becomes text on the phone). So for each message it:

1. Loads the pet's facts from the database. Even 100 rows is a tiny, fast query.
2. Gives each fact a score.
3. Sends the top 6 to the model with your message.

### What a fact stores (saved when the fact is created)

```
fact:        "Has an exam on Friday"
kind:        event            ← or lasting
importance:  2                ← 0 small, 1 normal, 2 big (people, pets, life events)
tags:        exam, test, school, university   ← written by the model when it saves the fact
follow_up:   2026-10-11       ← events only: when to ask how it went
last_used:   2026-10-08       ← last time it was sent to the model
```

The model fills in `kind`, `importance` and `tags` **once, when it saves the fact**, in the same call that writes the reply. After that, choosing facts uses no model at all.

### The score

| Signal | Points | Why |
|---|---|---|
| A tag matches a word in your message | **+5** per match | you're talking about it right now |
| Its follow-up date has come | **+4** | time to ask "How did the exam go?" |
| Importance | **+0 / +1 / +2** | your sister matters more than "likes pizza" |
| Not sent in the last few days | **+1** | rotation, so different things come up over time |
| Sent in the last hour | **−3** | so the pet doesn't repeat itself every message |

The top 6 scores go to the model.
