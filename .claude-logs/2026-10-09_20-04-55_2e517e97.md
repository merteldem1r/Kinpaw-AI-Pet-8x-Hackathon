## What item 3 is about

**Today, on your machine: nothing changes and nothing is broken.** Voice works as it should.

How it works now:
1. You talk to the pet. The talk route sends back the text reply, and **without waiting** it starts making the voice audio in the background (`startVoice`). The audio is stored in a map in the server's memory, keyed by the message id.
2. The phone shows the text, then asks the voice route for the audio. The voice route takes the audio that's already being made from that in-memory map (`takeVoiceJob`). That's why the voice arrives quickly.
3. A second in-memory map (`server/voice/once.ts`) remembers which replies were already spoken, so each reply is only voiced (and paid for) once.

That works because locally there's **one Node server that stays running**. The memory is shared between the two requests, and background work always gets to finish.

**The problem only appears once it's hosted on Vercel**, where each request can land on a different short-lived server instance:
- **The background work can be cut off.** Vercel can freeze a function as soon as it has sent its response. The voice started in step 1 may stall or never finish, so the phone waits longer for its voice.
- **The voice request may land on a different instance.** That instance's memory is empty, so it finds no job and makes the voice again (`speakNow`). The person still gets their voice, but it's slower, and you may pay the voice provider twice for the same reply.
- **"Spoken once" isn't guaranteed across instances.** Each instance has its own memory, so the same reply can occasionally be voiced twice. The code already accepts this, because the voice window and the daily limits put a cap on it.

None of these break anything for the person. The voice route already falls back to making the voice itself. The cost is **speed and money**, not correctness.

**The fix, when you deploy:**
- Wrap the background start in Next's `after()`, which keeps the function alive until that work finishes.
- If you're running several instances, move the two maps into the database (or Redis) so every instance sees the same jobs and claims.

Since this build is localhost only, my recommendation is to **not change anything now**. It's already written up under "Phase 5: before launch" in the plan, and I'd leave it there.
